## 1. What this project is, in one minute

- **Jev** is a model from TypeSafe. You send it a `state` (any JSON) and a set of **typed questions**,
  and it answers all of them in one call: a choice question returns a probability for every option plus
  a confidence, a score question returns a position on a rubric, a yes/no question returns the
  probability of yes. It never returns prose.
- **This repository** is a demo site that puts those questions to real financial work: ledgers, orders,
  fraud, wallets, portfolios, trades, filings, strategies. Fifty demos are specified in `prps/`; two
  exist so far.
- **The deployed site is static.** It replays answers that were recorded once and committed to the
  repository. No API key, no server, no network. Recording is the only paid step and it is the owner's
  decision, never yours.
- There is also a **backtest lab** under `/lab`, older than the demo site. You will not touch it.

Read these three files before writing code, in this order:

1. `prps/README.md` — how a PRP works and the layout of the repo.
2. `prps/004-demo-runtime.md` — the contract your demo must satisfy.
3. `demos/ledger-integrity/demo.js` — the demo built last, and the closest model for yours.

## 2. Concurrency: the rules that matter most

Other agents are building other demos from the same `main` at the same time. One is starting demo 103
(expense posting) shortly. Nothing you do may block or overwrite them.

### 2.1 Branch and commits

```bash
git fetch origin                          # if a remote exists; this repo may still be local-only
git switch -c demo/102-bank-reconciliation 9cab67d
```

- Commit only your own paths, named explicitly. **Never `git add -A` or `git add .`** from the repo
  root: it would sweep up another agent's half-finished files.
  ```bash
  git add demos/bank-reconciliation scripts/generate/bank-reconciliation.js \
          data/synthetic/bank-reconciliation.labels.json test/bank-reconciliation.test.js
  git add demos/index.js scripts/generate/index.js          # shared, one line each; see 2.2
  ```
- Commit messages describe the change and nothing else. No attribution lines, no tool names, no
  "generated with" footers. This is a hard rule in this repository; the owner publishes it publicly.
  Look at `git log` for the house style: a short subject, a blank line, then plain prose that says what
  changed and why.
- Rebase onto `main` before you hand back (`git switch main && git pull && git switch - && git rebase main`).
  Never force-push a shared branch, never amend or rebase a commit you did not write.
- Do not commit `web/dist/`, `results/`, `screenshots/` (already ignored) and do not commit the
  `web/src/generated/code-index.json` rebuild unless your demo changed it — it is regenerated by the
  build and a needless diff there conflicts with everyone.

### 2.2 Shared files: three of them, one line each

These are the only files outside your own folder that you may change. Keep the edit to the minimum,
keep the existing order, and do not reformat anything around it.

**Do not touch** (other agents depend on them and they are shared infrastructure):

If you are convinced the shared runtime needs a change, stop and write the reason in your hand-back

### 2.3 Processes, ports and money

## 3. How a demo is put together

A demo is one folder plus one registry line. The page, the replay, the answer cards, the report widgets
and the code panel are shared and you write none of them.

```
demos/bank-reconciliation/
  demo.js         the whole demo: metadata, state builder, questions, evaluation, report
  data.json       the dataset, written by your generator, committed
  fixtures.json   recorded answers, written by the recorder, committed
  notes.md        the explainer: what the data is, what was planted, what the run found
scripts/generate/bank-reconciliation.js     the seeded generator
data/synthetic/bank-reconciliation.labels.json   ground truth, written by the generator
test/bank-reconciliation.test.js            your tests
```

### 3.1 The dataset envelope

Every `data.json` has the same shape, validated by `demos/lib/dataset-shape.js`:

```json
{
  "id": "bank-reconciliation",
  "class": "synthetic",
  "generatedAt": "2026-09-19",
  "seed": 1102,
  "source": "scripts/generate/bank-reconciliation.js",
  "context": { "anything shared by every item": true },
  "items": [{ "id": "S-0001" }]
}
```

Item ids are unique and stable; the site deep-links to them with `?item=S-0001`.

### 3.2 Ground truth

Your generator plants problems on purpose and writes what it planted to
`data/synthetic/bank-reconciliation.labels.json` — **outside the demo folder**, so a state builder
cannot import it by accident. The report reads labels to grade the run. A contract test greps every
state for planted values and fails if one leaks.

### 3.3 The demo object

`demos/<slug>/demo.js` default-exports:

```js
export default {
  id, title, domain: 'books', value, tags, dataClass: 'synthetic', readMinutes, view,
  status: 'pending-recording',            // remove once fixtures exist
  itemLabel: (item) => '…',
  data: () => import('./data.json'),      // browser-only, lazy
  fixtures: () => import('./fixtures.json'),
  labels: () => import('../../data/synthetic/bank-reconciliation.labels.json'),
  buildState, questions, evaluate, report,
  explain: { data, state, questions, evaluate },   // "path#region" keys, see 3.6
};
```

- `buildState(item, context)` is **pure** and returns exactly what is sent to the model. `context` is
  the dataset's own `context` plus `items` (every row), so you can look across the dataset.
- `questions` uses the helpers in `demos/lib/questions.js` (`choice`, `score`, `noul`). Do **not**
  import the TypeSafe SDK in a demo; the helpers produce the identical shape and a test proves it.
- `evaluate(answers, item, context)` returns the small object the page shows: flags, a label, numbers.
- `report(results, context)` returns `{ note, findings, kpis, distribution, matrix, curve, checks, topItems }`
  — all optional except `kpis`. `context.labels` holds the ground truth.

### 3.4 Views

`view` names how one item is drawn: `table` (generic field list), `ledger` (document lines with
debit/credit columns, keyed on `item.documentId`), `queue` (alert card). 102 shows a statement line
against candidate ledger entries, which none of these draws well. Two acceptable options:

1. **Preferred:** use `view: 'table'` for now and say in your hand-back that 102 wants a
   `reconciliation` view (two columns: the statement line, then its candidates with the chosen one
   marked). Someone owning the shared runtime adds it.
2. If the owner tells you to add the view yourself, it goes in `web/src/demo/views/` plus one line in
   `web/src/demo/views/index.jsx`, and that file becomes a fourth shared file.

Do not fake a view by putting JSX in your demo folder.

### 3.5 Recorded answers

`fixtures.json` maps item id → the answers the API returned. The score answers are stored **without**
their rubric (`demos/lib/answers.js` strips it on write and restores it on read), so never hand-write
or hand-edit a fixture file.

Until recording happens, commit this placeholder, or the bundler cannot resolve the import:

```json
{
  "demo": "bank-reconciliation",
  "model": null,
  "recordedAt": null,
  "source": "not recorded yet — run: npm run record bank-reconciliation",
  "answers": {}
}
```

### 3.6 The code panel

Every demo page shows four real snippets: the data, the state, the questions, the evaluation. They are
extracted at build time from `// #region <key>` … `// #endregion` markers in the source, and
`demo.explain` points at them:

```js
explain: {
  data: 'scripts/generate/bank-reconciliation.js#demo:data',
  state: 'demos/bank-reconciliation/demo.js#demo:state',
  questions: 'demos/bank-reconciliation/demo.js#demo:questions',
  evaluate: 'demos/bank-reconciliation/demo.js#demo:evaluate',
}
```

**A shown region must be at most 40 lines or the build fails.** That is deliberate: those four blocks
are read aloud in a video, so keep helpers outside the region.

## 4. What to build, specifically

The specification is `prps/102-bank-reconciliation.md`. This is the same thing with the decisions the
last build settled.

### 4.1 Data (`scripts/generate/bank-reconciliation.js`, seed 1102)

One bank account, one month. 240 statement lines and 232 ledger entries; an amount-and-date rule
pre-clears the obvious 180, leaving **60 open items as the dataset's items**. Each open item carries up
to five candidate ledger entries, chosen by a deterministic rule that you write and describe in
`notes.md` — the model's job is judgement, not search.

Plant, and label: 12 timing differences, 9 unbooked bank fees, 7 FX differences on a second currency,
8 partial payments, 6 duplicates, 5 entries missing from the books, and 13 that simply match despite a
messy reference. Labels: `{ statementLineId, matchesEntryId | null, breakReason, problemId }`.

Reuse the helpers: `scripts/generate/lib/random.js` (seeded; never `Math.random`),
`lib/names.js` (invented merchants, people, banks — no real names, no real IBANs, no real card
numbers), `lib/money.js` (amounts with human rounding).

Budgets: dataset under 500 KB, and roughly 0.9 KB of fixture per item once recorded.

### 4.2 State

The statement line, its five candidates in full, the account's opening and closing balances, the period,
and the bank's reference format. Nothing that says which candidate is intended, and no label fields.

### 4.3 Questions (four)

`best_match` (choice: `CANDIDATE_1`…`CANDIDATE_5`, `NONE`), `match_quality` (score 0–6),
`break_reason` (choice: `TIMING`, `BANK_FEE`, `FX_DIFFERENCE`, `PARTIAL_PAYMENT`, `DUPLICATE`,
`MISSING_IN_BOOKS`, `MATCHED`), `auto_clear` (yes/no). Give every option a one-line description; the
page shows them.

### 4.4 Report

Auto-clear rate at the chosen quality threshold, precision against the labels, break reasons as a
distribution, the money still unreconciled, and a coverage curve from quality threshold to human
workload. Count **problems**, not rows, where a problem spans more than one row. Use the shared widgets
via the report shape: `kpis`, `distribution`, `matrix`, `curve`, `checks`, `topItems`, `findings`.

The `findings` line is worth copying from 101: it names the largest cluster of look-alike mistakes
instead of reporting them as dozens of separate ones. A repeated disagreement usually means the data is
arguable, not that the model is broken.

### 4.5 Tests (`test/bank-reconciliation.test.js`)

Model them on `test/ledger-integrity.test.js`:

- the dataset has the planted counts it claims;
- the state contains the candidates and no label text;
- a perfect set of stand-in answers scores every problem caught and zero false alarms;
- a lazy set ("everything is a timing difference") scores badly in the way you expect;
- the coverage curve is monotonic.

Stand-in answers are built in the test file, not recorded. No test may hit the network.

## 5. Traps that cost time in the last build

1. **The browser can break while every test passes.** An import was dropped from the replay path in
   `web/src/lib/demo-client.js`; all 49 node tests stayed green and every run in the page threw. Always
   finish with a real browser check (§6.3) before you say it works.
2. **Token estimates from `chars / 4` are about three times too low** for this kind of structured JSON.
   The ledger demo was estimated at 221K input tokens and cost 679K. If you need an estimate for the
   owner, record **three** items first, read the real usage the recorder prints, and multiply.
3. **`fixtures.json` must exist before `npm run build`**, even empty, or Vite cannot resolve the import.
4. **Regions over 40 lines fail the build**, with the demo id in the message. Keep helpers outside.
5. **Determinism is enforced.** `npm run generate <slug>` twice must leave `git status` clean. Sort
   anything you build from a `Map` or `Set` before writing it.
6. **Do not put ground truth in the dataset.** No `isDuplicate`, no `expectedMatch` fields on items.
   The contract test greps for planted strings and fails.
7. **Windows shell notes.** Use bash heredocs for multi-line commit messages, not PowerShell
   here-strings. For multi-line source edits prefer a small Python script over shell quoting. Use
   `pathToFileURL` when importing an absolute path in a script. Kill stale `msedge.exe` before a
   headless run, and pass **absolute** paths for the user-data directory.
8. **The runtime deep-links items** with `?item=<id>` and `?item=<id>&phase=scored`. Keep ids short and
   URL-safe.
9. **`status: 'pending-recording'`** must be on the demo object until fixtures exist; a contract test
   fails if a demo claims to be recorded and is not, and also fails if a fully recorded demo still
   claims to be pending.
10. **Your demo appears in the catalog the moment you add it to `DEMOS`.** With the pending status it
    shows an "Answers not recorded yet" badge and the run buttons are disabled. That is the intended
    intermediate state; do not hide the demo instead.

npm run check                    # size budgets, then the tests

### 6.2 Useful reads

```bash
node -e "const d=require('./demos/bank-reconciliation/data.json');console.log(d.items.length)"
node scripts/build-code-index.js        # fails loudly if a region is missing or too long
```

### 6.3 Look at it in a browser, safely

```bash
npm run build
npm run serve:static -- web/dist 3210
```

Then open `http://127.0.0.1:3210/demos/bank-reconciliation`, and stop the server when you are done. It
serves the build exactly as the deploy does: static files, SPA fallback, **no API** — a call to
`/api/*` returns 404 and is logged, so a demo that tries to reach the model shows up immediately. Use
this rather than the Express server, which reads `.env` and makes the page live-capable.

### 6.4 Recording (owner's decision, not yours)

```bash
node scripts/record-demo.js bank-reconciliation --dry-run     # free, prints what it would send
node scripts/record-demo.js bank-reconciliation --items S-0001,S-0002,S-0003   # three, for a real estimate
npm run record bank-reconciliation                            # the full run, only after approval
```

The recorder retries each item once, saves every 25 items, and skips items that already have answers,
so a full run can be resumed.
